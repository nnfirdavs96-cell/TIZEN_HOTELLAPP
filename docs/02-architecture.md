# 02. Техническая архитектура

## Обзор системы

Три клиента, один бэкенд, общие данные:


## Технологический стек

| Слой | Технология | Версия/вариант | Обоснование |
|------|-----------|----------------|-------------|
| TV-клиент | HTML5 + CSS3 + **TypeScript** (vanilla, сборка Vite) | ES2017 target | Старые TV → минимум рантайма (ADR-002) |
| Бэкенд | **Node.js 20 LTS + NestJS** | TypeScript | Единый язык, общие типы, модульность (ADR-001) |
| Реальное время | **Socket.IO** поверх WebSocket | — | Чат, статусы, уведомления; авто-reconnect |
| БД | **PostgreSQL 16** | — | Реляционные данные, транзакции |
| Кэш/очереди | **Redis 7** | — | Сессии, pub/sub, BullMQ-очереди |
| Панель | **React 18 + TypeScript + Vite** | — | Богатый UI на десктопе |
| Стейт-панель | TanStack Query + Zustand | — | Серверный кэш + лёгкий локальный стейт |
| Платежи | Провайдер с токенизацией (Stripe / локальный эквайринг) | — | PCI-минимизация (ADR-004) |

| Контейнеры | Docker + docker-compose (dev), оркестрация на проде | — | Воспроизводимость окружений |

| Наблюдаемость | Структурные логи (pino) + метрики (Prometheus) + Sentry | — | Диагностика прод-инцидентов |

## Структура репозитория

Монорепозиторий на **pnpm workspaces** (общие типы между TV-app, панелью и API — единый источник правды для контрактов).

```
tizen_hotellapp/
├── apps/
│   ├── tv-app/          # Tizen Web App (клиент на TV)
│   ├── staff-panel/     # React SPA (персонал)
│   └── api/             # NestJS (REST + WS + интеграции)
├── packages/
│   ├── shared-types/    # DTO/контракты API (импортируются всеми)
│   └── ui-kit/          # дизайн-токены, общие стили фокуса
├── infra/
│   ├── docker/          # Dockerfile + compose
│   ├── db/              # миграции + сиды
│   └── ci/              # пайплайны
└── docs/
```

**Почему монорепозиторий:** один PR может менять контракт API и сразу обновлять типы во всех клиентах; меньше рассинхрона; единый CI. Минус — нужна дисциплина границ модулей (решается линтами и code review).

## Архитектура бэкенда (модульная, NestJS)

Каждый функциональный модуль — отдельный NestJS-модуль со своим контроллером, сервисом, репозиторием:

```
api/src/
├── modules/
│   ├── auth/          # JWT, привязка к устройству/номеру, PIN
│   ├── booking/       # брони, check-in/out, счёт
│   ├── food/          # меню, корзина, заказы еды
│   ├── shop/          # каталог магазина, заказы
│   ├── taxi/          # заказ такси (через TaxiProvider)
│   ├── chat/          # сообщения, сервис-запросы (WebSocket)
│   ├── info/          # контент об отеле (расписания, карта, FAQ)
│   ├── payments/      # charge-to-room, фолио, провайдер
│   └── admin/         # управление контентом, пользователи, аналитика
├── integrations/      # внешние адаптеры за интерфейсами
│   ├── pms/           # PmsAdapter (OPERA OHIP / generic / mock)
│   ├── taxi/          # TaxiProvider (диспетчерская / deep-link / mock)
│   ├── payment/       # PaymentProvider (Stripe / локал. эквайринг / mock)
│   └── notify/        # Email/SMS (отправка счёта, коды)
├── common/            # guards, interceptors, фильтры ошибок, идемпотентность
└── realtime/          # WebSocket-gateway (Socket.IO), комнаты, события
```

**Принцип:** все внешние сервисы спрятаны за интерфейсами (`PmsAdapter`, `TaxiProvider`, `PaymentProvider`). Это позволяет (а) разрабатывать на mock-адаптерах без реальных договоров, (б) менять провайдера без переписывания модулей.

## Архитектурные решения (ADR)

Кратко зафиксированные решения с альтернативами и последствиями.

### ADR-001: Backend на Node.js + NestJS (а не Python/FastAPI)
- **Контекст:** исходный план допускал «Node.js или FastAPI».
- **Решение:** **NestJS (TypeScript).**
- **Почему:** единый язык с TV-app и React-панелью → общие типы из `packages/shared-types`, один пул компетенций у frontend-разработчика, меньше контекст-свитчинга в команде из 2–3 человек.
- **Альтернатива:** FastAPI — отличный выбор, если в команде сильнее Python. Допустим как замена; контракты API от языка не зависят.
- **Последствия:** нужен дисциплинированный TypeScript; выигрыш — переиспользование DTO.

### ADR-002: TV-приложение на vanilla JS/TS (а не React)
- **Контекст:** TV 2016–2019 имеют ~512 МБ–1 ГБ RAM и слабый CPU.
- **Решение:** клиент на **vanilla HTML/CSS/TypeScript** + минимум зависимостей, своя лёгкая система маршрутизации и фокуса.
- **Почему:** держим JS-бандл < 250 КБ gzip и RAM < 100 МБ; полный контроль над фокус-навигацией.
- **Альтернатива:** Preact (≈4 КБ) — допустим, если понадобится компонентная модель; React/Vue — нет (риск для старых TV).
- **Последствия:** больше ручного кода UI, зато предсказуемая производительность.

### ADR-003: Авторизация по номеру комнаты + PIN с привязкой к устройству
- **Решение:** TV провижинится с `room_id` + `device_token`; гость подтверждает вход PIN-кодом/кодом брони. JWT привязан к устройству и номеру.
- **Почему:** TV физически в номере → «владение устройством» = слабый фактор; PIN/код брони добавляет подтверждение личности; при выезде сессия инвалидируется.
- **Последствия:** нужна процедура провижининга (см. [06](./06-tizen.md)) и сброс сессии на Check-out.

### ADR-004: Платежи — charge-to-room по умолчанию, PCI-минимизация
- **Контекст:** ввод карты пультом на TV небезопасен и втягивает всю систему в PCI DSS.
- **Решение:** основной способ — **списание на счёт номера (фолио)** с расчётом при выезде; онлайн-оплата картой — только через провайдера с токенизацией и/или передачу оплаты на телефон гостя по **QR-коду** (Payment Link). Мы **не храним и не передаём через себя данные карт**.
- **Почему:** снижает зону PCI до SAQ-A, убирает мучительный ввод карты пультом, опирается на существующие процессы отеля.
- **Последствия:** обязательна связка с фолио/PMS (или ручной экспорт счёта в MVP); см. ADR-007.

### ADR-005: Стратегия голосовой связи (VoIP)
- **Контекст:** WebRTC на старых Tizen нестабилен/недоступен.
- **Решение:** **деградация по возможностям:**
  1. **Базово (все TV):** кнопка «Перезвоните мне» → задача ресепшену перезвонить на номер.
  2. **Всегда:** текстовый чат (WebSocket) как основной канал.
  3. **Опционально (Tizen ≥ 5.5, проверка фичей):** WebRTC-аудиозвонок TV→ресепшен.
- **Почему:** не обещаем то, что не работает на части парка; ценность (быстрая связь) обеспечивается чатом и callback.
- **Последствия:** в панели персонала нужен модуль обработки callback-запросов и чата.

### ADR-006: Офлайн-устойчивость
- **Решение:** статический контент (меню, инфо, расписания) кэшируется на TV; действия (заказ, запрос) ставятся в **локальную очередь** и отправляются с **идемпотентными ключами** при восстановлении сети; явный экран «нет связи».
- **Почему:** гостиничные сети нестабильны, а потеря заказа/двойное списание недопустимы.
- **Последствия:** все мутирующие эндпоинты принимают `Idempotency-Key`; UI показывает статусы «отправляется/отправлено».

### ADR-007: Интеграция с PMS
- **Решение:** слой `PmsAdapter` за интерфейсом; реализации: `mock` (Фазы 1–2), `generic-csv/export` (MVP-пилот), `opera-ohip` (после пилота). Начисления на фолио идут через очередь с ретраями.
- **Почему:** интеграция с Opera/Fidelio долгая и зависит от отеля; нельзя блокировать разработку ядра.
- **Последствия:** в MVP счёт может экспортироваться вручную/полуавтоматически; полноценная синхронизация — отдельная веха.

### ADR-008: Реальное время на Socket.IO
- **Решение:** Socket.IO (поверх WebSocket) с комнатами по `room_id` и ролям персонала; Redis-adapter для масштабирования на несколько инстансов.
- **Почему:** авто-reconnect, fallback-транспорты, простые «комнаты»; Redis pub/sub для горизонтального масштабирования.
- **Последствия:** состояние соединений — в Redis, не в памяти процесса.

## Поток данных: пример «заказ еды»

```
TV: добавить блюда → корзина (локально)
TV: «Оформить» → POST /orders (Idempotency-Key) ──▶ API
API: валидирует, создаёт order(status=NEW), пишет в PostgreSQL
API: charge-to-room → начисление на фолио (через PmsAdapter, очередь)
API: WS-событие order.created ──▶ комната «kitchen» (панель кухни)
Кухня: меняет статус (ACCEPTED→COOKING→DELIVERING→DONE)
API: WS-событие order.updated ──▶ комната TV (room_id)
TV: показывает статус в реальном времени
```

## Нефункциональные требования (NFR)

| Категория | Требование |
|-----------|-----------|
| Производительность | TTI TV < 3 c (TV 2017); P95 REST < 400 мс |
| Масштаб | До 500 номеров на инстанс-набор; горизонтальное масштабирование API |
| Надёжность | Uptime API ≥ 99.5%; идемпотентные мутации; ретраи интеграций |
| Безопасность | TLS везде; JWT с ротацией; PCI SAQ-A; 152-ФЗ/GDPR (см. [08](./08-security-compliance.md)) |
| Локализация | RU/EN из коробки, расширяемо |
| Наблюдаемость | Логи/метрики/трейсы; алерты на ошибки и latency |
| Совместимость | Tizen 4.0+ обязательно, мягкая поддержка 3.0 |
