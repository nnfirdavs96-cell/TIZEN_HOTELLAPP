# 10. Деплой и эксплуатация

Чего не было в исходном плане: окружения, CI/CD, мониторинг, бэкапы, процедура установки в отеле. Здесь всё это.

## Окружения

| Окружение | Назначение | Данные |
|-----------|-----------|--------|
| **dev (локально)** | Разработка | docker-compose: PostgreSQL + Redis + mock-провайдеры |
| **staging** | Интеграционные/e2e тесты, демо | Тестовые данные, mock или sandbox провайдеров |
| **production** | Пилотный отель и далее | Реальные данные, реальные провайдеры |

- Конфигурация — через переменные окружения (`.env`, секрет-менеджер). В git — только `.env.example`.
- Разные секреты и БД на каждое окружение.

## Локальная разработка

```bash
pnpm install
docker compose -f infra/docker/docker-compose.dev.yml up -d   # PostgreSQL + Redis
pnpm --filter api db:migrate && pnpm --filter api db:seed
pnpm --filter api dev          # бэкенд
pnpm --filter staff-panel dev  # панель
pnpm --filter tv-app build     # → запуск .wgt в эмуляторе Tizen Studio
```

## CI/CD (GitHub Actions)

**На каждый PR (`ci.yml`):**
1. Установка зависимостей (кэш pnpm).
2. Линт + типчек.
3. Unit + component + integration (Testcontainers: PG/Redis).
4. E2E панели (Playwright headless).
5. Сборка образов API/панели + сборка TV-`.wgt`; проверка бюджета размера бандла.
6. Сканирование секретов (gitleaks) и зависимостей (audit).

**На мерж в `develop` (`deploy-staging.yml`):**
- Сборка и публикация образов → деплой на **staging** → миграции БД → smoke-тесты.

**На тег/релиз в `main` (`deploy-prod.yml`):**
- Ручное подтверждение (approval) → деплой на **production** → миграции → smoke → уведомление.
- TV-`.wgt` собирается, подписывается сертификатом, публикуется как артефакт релиза (далее установка в отеле — см. ниже).

**Стратегия БД-миграций:** только вперёд-совместимые шаги (expand/contract), чтобы деплой не ронял работающие инстансы. Миграции — отдельный шаг до старта новых подов.

## Контейнеризация и развёртывание

- **API** и **панель** — Docker-образы; раздача панели как статика через Nginx/CDN.
- Оркестрация прод — по масштабу: для пилота достаточно одного хоста (docker-compose/systemd) или managed-платформы; при росте — Kubernetes.
- **API масштабируется горизонтально** (stateless); состояние сессий/сокетов — в Redis (Socket.IO Redis-adapter).
- Reverse-proxy (Nginx/Traefik): TLS-терминация, rate limiting, gzip/brotli, заголовки безопасности.

## Хостинг и сеть

- **TLS** обязателен (Let's Encrypt/корпоративные сертификаты).
- Для РФ-отелей учесть **152-ФЗ** (хранение ПДн в РФ) при выборе провайдера ([08](./08-security-compliance.md)).
- TURN/STUN (coturn) — отдельный хост для WebRTC (если включаем VoIP).
- Резерв по сети: TV-приложение устойчиво к коротким разрывам (ADR-006).

## Наблюдаемость (observability)

| Сигнал | Инструмент | Что мониторим |
|--------|-----------|---------------|
| **Логи** | pino (структурные JSON) → агрегатор (Loki/ELK) | ошибки, аудит, `traceId` |
| **Метрики** | Prometheus + Grafana | RPS, P95 latency, ошибки 5xx, длина очередей, WS-соединения |
| **Ошибки** | Sentry | исключения API и клиентов (панель; TV — по возможности) |
| **Алерты** | Alertmanager | всплеск 5xx, рост latency, отказ PMS-синка, падение очередей |
| **Health-checks** | `/health`, `/ready` | живость/готовность для оркестратора |

**Ключевые бизнес-метрики на дашборде:** заказы/час, средний чек, время до принятия заказа кухней, среднее время ответа в чате, доля заказов через офлайн-очередь, ошибки charge-to-room.

## Бэкапы и восстановление

- **PostgreSQL:** ежедневные полные бэкапы + WAL/PITR; шифрование бэкапов; хранение ≥ 30 дней.
- **Регулярная проверка восстановления** (раз в месяц — тестовый restore на staging). Бэкап без проверенного restore не считается бэкапом.
- **Redis:** не источник правды; восстанавливаемое состояние (сессии можно перевыпустить); при необходимости — AOF.
- **Контент/изображения:** объектное хранилище с версионированием.
- **RPO/RTO (цель пилота):** RPO ≤ 24 ч (PITR уменьшает), RTO ≤ 4 ч.

## Установка и обслуживание в отеле

1. **Провижининг сети:** TV в номерах подключены к Wi-Fi/Ethernet с доступом к API.
2. **Установка приложения:** `.wgt` ставится на каждый TV (Developer/Partner-сертификат) или через **Samsung Business TV (SSSP)** для парка.
3. **Режим киоска:** автозапуск приложения при включении TV, блокировка выхода в системное меню.
4. **Провижининг номера:** способ A (код-активация) — сотрудник привязывает TV к номеру ([06](./06-tizen.md)).
5. **Обновления приложения:** переустановка `.wgt` или удалённое обновление через SSSP/MDM; контент (меню/инфо) обновляется без переустановки (через админ-панель).
6. **Мониторинг устройств:** `devices.last_seen_at` — видеть «живые» TV; алерт на «пропавшие» TV.

## Управление конфигурацией отеля

- Каждый отель — запись `hotels` (таймзона, валюта, локаль, флаги функций).
- Включение/выключение модулей на отель через `hotels.settings` (например, такси выключено, если нет договора).
- Мультитенантность: данные изолированы по `hotel_id` на уровне запросов и прав.

## Runbook (типовые операции)

| Ситуация | Действие |
|----------|----------|
| PMS недоступен | Начисления копятся в очереди `folio-sync`, ретраи; алерт; ручной экспорт счёта при необходимости |
| Всплеск 5xx | Проверить дашборд/Sentry по `traceId`, откатить релиз при регрессии |
| TV «пропал» | Проверить `last_seen_at`, сеть номера, перезапустить приложение/TV |
| Утрата `deviceToken`/замена TV | Повторный провижининг (revoke старого устройства) |
| Подозрение на инцидент безопасности | Отзыв токенов/ключей, разбор по `audit_log`, уведомление отеля ([08](./08-security-compliance.md)) |
