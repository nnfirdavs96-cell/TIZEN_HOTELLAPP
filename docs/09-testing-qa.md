# 09. Тестирование и QA

Исходный план упоминал только «тестирование на реальных TV». Здесь — полная стратегия: уровни тестов, инструменты, матрица устройств, критичные сценарии.

## Пирамида тестов

```
        ╱╲     E2E (мало, критичные потоки)
       ╱──╲    Integration (API + БД + WS)
      ╱────╲   Component (UI-компоненты, фокус)
     ╱──────╲  Unit (бизнес-логика, утилиты) — много
```

| Уровень | Что покрываем | Инструменты |
|---------|---------------|-------------|
| **Unit** | Расчёт сумм, валидация, фокус-движок, утилиты i18n/формат | Vitest/Jest |
| **Component (TV)** | Экраны и фокусируемые компоненты, навигация стрелками | Vitest + jsdom + симуляция keydown |
| **Component (панель)** | React-компоненты | Vitest + React Testing Library |
| **Integration (API)** | Эндпоинты + БД + Redis + WS, идемпотентность, RBAC | Jest + Supertest + Testcontainers (PG/Redis) |
| **E2E** | Сквозные потоки гостя и персонала | Playwright (панель/веб), сценарии TV — на эмуляторе |
| **Device (ручное)** | Реальные TV: фокус, перф, WebRTC, overscan | Чек-листы на устройствах |

## Критичные сценарии (обязательны к покрытию)

**Гость (TV):**
1. Вход по PIN/коду → главное меню → Check-out с письмом.
2. Заказ еды: корзина → оформление «на счёт» → статус в реальном времени.
3. Идемпотентность: повтор заказа при сбое сети **не** создаёт дубль.
4. Офлайн: меню/инфо из кэша; заказ ставится в очередь и уходит при возврате сети.
5. Сервис-запрос (полотенца) и чат с ресепшен (реальное время, переотправка).
6. Такси: оценка → заявка → статус / fallback-режим.
7. Полная навигация пультом, включая Back (10009) на каждом экране.
8. RU/EN переключение, корректные форматы дат/валют.

**Персонал (панель):**
9. Кухня видит новый заказ < 3 c, меняет статусы, гость видит обновление.
10. RBAC: роль `kitchen` не видит админ-разделы; `admin` правит меню без релиза TV.
11. Чат: ответ ресепшена доходит на TV; маршрутизация заявок по ролям.

**Backend:**
12. Серверный пересчёт суммы (клиентская цена игнорируется).
13. Charge-to-room создаёт `folio_entry`; при недоступности PMS — очередь с ретраями.
14. Инвалидизация сессии на Check-out; доступ к чужому номеру запрещён (403).

## Матрица устройств (реальные TV)

Тестировать минимум на **3–5 моделях** разных лет (исходный план верно отмечал разницу поведения):

| Год / линейка | Tizen | Почему важно |
|---------------|-------|--------------|
| 2017 (нижний таргет) | 3.0 | Худшая производительность, проверка бюджета |
| 2018–2019 | 4.x | Массовый парк отелей |
| 2020–2021 | 5.5+ | WebRTC, более новые API |
| 2022–2023 | 6.x+ | Совместимость «вверх» |

На каждом устройстве — чек-лист: TTI, плавность списков, фокус/Back, overscan/безопасные поля, читаемость шрифтов, WebRTC (где заявлен), стабильность при долгой работе (память не течёт за сутки+).

## Производительность

- Замер **TTI** на TV 2017 (бюджет < 3 c), профилирование памяти (< 100 МБ), размер бандла (< 250 КБ gzip) — в CI как проверка размеров, на устройстве — вручную.
- **Нагрузочное** тестирование API (k6/Artillery): сценарий «пиковый ужин» — N номеров заказывают одновременно; цель P95 < 400 мс, без потери заказов.
- **Тест долгой работы (soak):** приложение на TV сутки+ без перезагрузки — нет утечек/деградации.

## Тест офлайна и сети

- Симуляция потери сети в середине заказа → заказ в очереди → доставка после восстановления, без дублей.
- Разрыв WebSocket → авто-reconnect → догрузка пропущенных сообщений/статусов.
- Медленная сеть (throttle) → интерфейс не блокируется, картинки ленивые.

## Безопасность (тест)

- Попытка доступа к чужому `room_id` с валидным токеном → 403.
- Брутфорс PIN → блокировка после лимита.
- Подмена суммы в запросе заказа → сервер игнорирует, считает сам.
- Проверка, что карты нигде не сохраняются; секреты не в бандле/логах.
- (Перед релизом) прогон `/security-review` по диффу и зависимостям.

## Автоматизация в CI

На каждый PR (см. [10](./10-deployment-ops.md)):
- Линт + типчек (TS).
- Unit + component + integration (Testcontainers поднимает PG/Redis).
- E2E панели (Playwright, headless).
- Сборка TV-`.wgt` и проверка бюджета размера.
- Отчёт о покрытии (цель: бизнес-логика ≥ 80%).

Ручные device-тесты — перед каждым релизом в отель (Фаза 4 и далее).

## Definition of Done по тестам (на задачу)

- [ ] Бизнес-логика покрыта unit-тестами.
- [ ] Критичный поток — integration/e2e.
- [ ] TV-экран проверен на эмуляторе пультом (keydown-симуляция) + на ≥1 реальном TV перед релизом.
- [ ] Офлайн/ошибки протестированы.
- [ ] RU/EN проверены.
