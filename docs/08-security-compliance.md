# 08. Безопасность и комплаенс

Исходный план ограничивался словом «JWT». Здесь — модель угроз, аутентификация, платёжная безопасность, защита персональных данных и секретов.

## Модель угроз (кратко)

| Угроза | Вектор | Митигация |
|--------|--------|-----------|
| Чужой доступ к сервисам номера | TV физически доступен; гость съехал | Вход по PIN/коду брони; инвалидизация сессии на Check-out; короткий TTL access-токена |
| Кража `deviceToken` | Доступ к устройству/прошивке | Хранение в защищённом хранилище Tizen; привязка токена к `device_id`+`room_id`; возможность revoke |
| Подмена суммы заказа | Клиент шлёт свою цену | **Серверный пересчёт** сумм; клиентским ценам не доверяем |
| Дубли заказов/двойное списание | Ретраи при плохой сети | `Idempotency-Key` на всех мутациях |
| Перехват трафика | Открытый Wi-Fi отеля | **TLS везде** (HTTPS/WSS), HSTS |
| Утечка данных карт | Хранение карт | **Не храним карты** (charge-to-room / токенизация провайдера) — PCI SAQ-A |
| Утечка PII (email, телефон, имя) | БД, логи | Шифрование «at rest», маскирование в логах, доступ по ролям, удаление по запросу |
| Брутфорс PIN | Перебор на входе | Rate limit + лимит попыток (`pin-fail:{bookingId}`), временная блокировка |
| Несанкционированный доступ персонала | Слабые пароли/роли | RBAC, хэш паролей (argon2/bcrypt), 2FA для админа (P1) |
| Атаки на API | Боты, флуд | Rate limiting, валидация DTO, WAF/reverse-proxy лимиты |

## Аутентификация и сессии

- **Гость:** `deviceToken` (устройство) + код брони/PIN (личность) → **JWT access (15 мин)** + **refresh (до Check-out / 30 дн в Redis)**. Access привязан к `room_id`+`device_id`; сервер проверяет соответствие ресурса номеру токена.
- **Ротация refresh:** при обновлении — новый refresh, старый инвалидируется (reuse detection).
- **Check-out:** немедленная инвалидизация всех токенов брони, очистка гостевых данных на TV.
- **Персонал:** email+пароль (argon2) → JWT с ролью; короткий access + refresh; выход инвалидирует сессию.
- **Хранение секретов на TV:** только `deviceToken` и кэш контента; никаких карт/паролей.

## Роли и доступ (RBAC)

| Роль | Доступ |
|------|--------|
| `reception` | Чаты, сервис-запросы, статус номеров, заказы (просмотр), callback |
| `kitchen` | Очередь заказов еды, смена статусов |
| `housekeeping` | Заявки уборки/полотенец, заказы магазина |
| `maintenance` | Заявки техника |
| `admin` | Всё выше + управление контентом/меню/ценами, пользователи, аналитика |

- Проверка роли на каждом `/v1/staff/*` и `/v1/admin/*` (guard).
- Принцип наименьших привилегий; действия пишутся в `audit_log`.

## Платежи и PCI DSS

**Решение (ADR-004):** минимизировать PCI-область.
- **Основной путь — charge-to-room:** сумма начисляется на фолио, расчёт при выезде через кассу/PMS отеля. Мы не касаемся карт.
- **Онлайн-оплата (опц.):** только через провайдера с **токенизацией** — Payment Link/Hosted Page, открываемый на **телефоне гостя по QR**. Данные карты вводятся на стороне провайдера, не на TV и не на нашем бэкенде.
- Мы храним только идентификаторы транзакций (`provider_payment_id`), не PAN/CVV.
- Это удерживает нас в **PCI DSS SAQ-A** (минимальные требования).
- Вебхуки провайдера — с проверкой подписи; суммы сверяются с заказом на сервере.

## Защита персональных данных (152-ФЗ / GDPR)

PII в системе: имя, email, телефон гостя; история заказов/чатов.
- **Минимизация:** собираем только необходимое (email — для счёта, телефон — для callback такси).
- **Шифрование at rest** для БД и бэкапов; TLS in transit.
- **Хранение:** ограниченный срок (например, удаление/анонимизация гостевых PII через N дней после выезда — согласовать с отелем и законом).
- **Право на удаление/доступ:** механизм удаления PII по запросу (жёсткое удаление гостевых данных, обезличивание заказов для статистики).
- **Согласие:** на Lock/первом экране — короткое уведомление о обработке данных и политика конфиденциальности.
- **Логи без PII:** маскировать email/телефон в логах; не логировать тела чатов в открытом виде.
- **Локализация данных (152-ФЗ):** для РФ — хранение персональных данных граждан на серверах в РФ (учесть при выборе хостинга).

## Секреты и конфигурация

- Секреты (ключи провайдеров, JWT-секрет, доступы к БД) — **только** в секрет-менеджере/переменных окружения, **никогда** в git.
- В репозитории — только `.env.example` с описанием переменных.
- Ротация ключей; разные секреты для dev/staging/prod.
- Сканирование секретов в CI (gitleaks/secret scanning).

## Сетевая безопасность

- TLS 1.2+ обязателен; HSTS; современные шифры.
- Reverse-proxy (Nginx/Traefik) с rate limiting и таймаутами перед API.
- CORS: панель — со своего домена; TV-app — строгий список origin/headers.
- WebSocket: авторизация по JWT при connect; проверка комнаты при подписке (гость не может слушать чужой номер).

## Аудит и реагирование

- `audit_log` на чувствительные действия (вход, начисление, смена контента/цен, удаление PII).
- Алерты на аномалии: всплеск ошибок auth, 5xx, неуспешные списания.
- План реагирования на инцидент: отзыв токенов/ключей, уведомление отеля, разбор по `traceId`/логам.

## Чек-лист безопасности к релизу (Фаза 4)

- [ ] TLS везде, HSTS включён.
- [ ] JWT: короткий access, ротация refresh, инвалидизация на Check-out.
- [ ] Серверный пересчёт всех сумм; идемпотентность мутаций.
- [ ] PCI: карты не хранятся; онлайн-оплата — через провайдера (SAQ-A).
- [ ] PII зашифрованы at rest; логи без PII; политика удаления.
- [ ] RBAC на staff/admin; пароли argon2; (P1) 2FA админа.
- [ ] Rate limiting на auth/orders/requests; лимит попыток PIN.
- [ ] Секреты вне git; сканирование секретов в CI.
- [ ] Бэкапы БД зашифрованы и проверены на восстановление.
